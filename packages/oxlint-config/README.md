# @taiki-kuraishi/oxlint-config

SKILL の規約を表す oxlint の共有設定と、自作ルールの JS plugin。

自作ルールの診断と共有設定で追加する診断メッセージは英語で表示する。ルール ID・messageId・検出条件は表示言語に依存しない。

## 責務

- 実装すること: kstack の SKILL ごとの oxlint 共有設定（`extends` に渡す設定オブジェクト）。SKILL の規約は explicit なルール設定と、既存ルールで表せない規約の自作ルール（JS plugin）で表す。加えて、設定ごとに利用先に合わせた `categories` の有効化と、SKILL と逆を向く・または規約に無い書き方を強いるルールの `"off"`（理由はその節の off の表）
- 実装しないこと: oxfmt の設定、SKILL に対応する節の個別設定に既存ルールを列挙すること（SKILL の規約を表すものは explicit に設定し、`categories` で入るものは lint が agent に伝えるので、対応表には書かない）、型情報を使うルール（oxlint の JS plugin は型情報を使えない）

## SKILL と設定の対応

export する設定は SKILL の名前から `kstack-` を除いた名前にする（`kstack-tanstack-query` → `tanstackQuery`）。既存ルールで表せない規約は、`src/rules/` に自作ルールを置き、plugin `kstack`（`@taiki-kuraishi/oxlint-config/plugin`）から export する。表せない規約は、lint で守れないのでレビューで確かめる。

### kstack-typescript（`typescript`）

| 規約                                                           | ルール / 表せない理由                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 導出できる型を手書きしない                                     | `kstack/no-explicit-return-type`。type predicate・`asserts` は除く。導出できない再帰関数は disable コメントで理由を残す。戻り値のためだけの `interface` / `type` は検出しない                                                                                                                                                                                                  |
| else・三項演算子を使わない。早期 return する                   | `kstack/no-else`、`no-ternary`                                                                                                                                                                                                                                                                                                                                                 |
| 制御フローのネストを 2 段までにする                            | `max-depth`（`max: 2`）。`if` 内の `if`・ループ内の `if` は許可し、3 段以上を指す。ループ・`switch`・`try` なども深さに数える。関数ごとに数え直すため、コールバック内の分岐は外側の深さに加算しない                                                                                                                                                                            |
| `if` の前には空行を置く                                        | `kstack/blank-line-before-if`                                                                                                                                                                                                                                                                                                                                                  |
| 関数の引数はオブジェクトに構造化する                           | `kstack/object-params`。呼び出しの引数にその場で書く関数（コールバック）と `this` 引数は除く。名前を付けて参照で渡すコールバックは検出するので、disable コメントで理由を残す                                                                                                                                                                                                   |
| 条件付きオブジェクト spread を使わない                         | `kstack/no-conditional-spread`                                                                                                                                                                                                                                                                                                                                                 |
| 小さすぎる処理を関数化しない                                   | 表せない。「小さい」「名前に意味がある」を構文から決められない                                                                                                                                                                                                                                                                                                                 |
| 各メソッドで繰り返す依存の生成は constructor に置く            | 表せない。依存の生成と同じ関数の呼び出しを構文から区別できない                                                                                                                                                                                                                                                                                                                 |
| プロパティを読むだけの分割代入をしない                         | `kstack/no-property-destructure`。`const { ... } = args`・`= args.update`・`= this`・`= this.session` のように、名前で参照できるオブジェクトからの分割代入を指す。関数呼び出しと `await` の戻り値、rest を含む `const { id, ...rest } = obj`、初期化子の無い `for (const { id } of items)`、関数の引数、配列の分割代入は除く。`args!` のような TS の式で包んだ初期化子は見逃す |
| class でしか使わない関数は private method にする               | 表せない。1 つの class だけが呼ぶかは同じファイルの中なら数えられるが、定数の初期化や他の関数からの呼び出しと合わせて判断が要るので、レビューで確かめる                                                                                                                                                                                                                        |
| class・error・定数・型が同居するファイルはディレクトリに分ける | 表せない。ファイルの分け方と `index.ts` から何を export するかはディレクトリ構成の判断で、1 ファイルの AST からは決まらない                                                                                                                                                                                                                                                    |

規約ではないが、`categories` の `correctness`・`perf`・`restriction`・`style`・`suspicious` を `"error"` にする（kstack の利用先の設定に合わせる）。一括で有効になるルールのうち、SKILL の規約と逆を向くもの・規約に無い書き方を強いるものは `"off"` にする。`no-ternary` は kstack-typescript の規約なので `"error"` のまま残す。

| `"off"` にするルール                                                                                                            | 理由                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `class-methods-use-this`                                                                                                        | `this` を使わない private method（kstack-typescript の「class でしか使わない関数は private method にする」、kstack-layerd-architecture の「class 専用の処理は private method にする」の形）を指させない                                                                                                     |
| `typescript/no-extraneous-class`・`unicorn/no-static-only-class`・`unicorn/consistent-function-scoping`                         | class 専用の処理を class の外へ出させる方向に押し、上と同じ規約と逆を向く（`unicorn/no-static-only-class` は `pedantic` で一括有効にはならないが、利用側が `pedantic` を有効にしたときのために切る）                                                                                                        |
| `unicorn/prefer-ternary`                                                                                                        | if / else を三項演算子に書き換えさせ、`no-ternary` と `kstack/no-else` と逆を向く                                                                                                                                                                                                                           |
| `unicorn/require-module-specifiers`                                                                                             | 設定をまだ持たない package の entry は `export {};` が要り、空にすると `unicorn/no-empty-file` が指すので、どちらでも書けなくなる                                                                                                                                                                           |
| `unicorn/throw-new-error`                                                                                                       | kstack-better-result のエラー定義 `class UserNotFoundError extends TaggedError("UserNotFoundError")<{ ... }>() {}` は名前が `Error` で終わる関数を `new` 無しで呼ぶ。oxlint の実装は `throw` の中に限らず `Error` で終わる名前の呼び出しをすべて指し、`TaggedError` は `new` で呼ぶものではないので直せない |
| `typescript/explicit-function-return-type`・`typescript/explicit-module-boundary-types`                                         | `kstack/no-explicit-return-type`（戻り値の型を書かない）と逆を向く                                                                                                                                                                                                                                          |
| `oxc/no-async-await`・`oxc/no-optional-chaining`・`oxc/no-rest-spread-properties`・`no-undefined`・`unicorn/no-null`・`no-void` | 言語機能そのものを禁じ、SKILL の例（`?.`、`...`、`=== undefined`、`=== null`）が書けなくなる                                                                                                                                                                                                                |
| `eslint/max-statements`・`max-params`・`id-length`・`no-magic-numbers`                                                          | 直列の処理や短い名前を lint のためだけに分割・改名させる                                                                                                                                                                                                                                                    |
| `func-names`・`func-style`・`new-cap`・`object-shorthand`・`unicorn/no-anonymous-default-export`                                | SKILL に無い書き方の好みを強いる                                                                                                                                                                                                                                                                            |
| `prefer-destructuring`                                                                                                          | `const userId = args.update.userId` を `const { userId } = args.update` に書き換えさせ、kstack-typescript の「プロパティを読むだけの分割代入をしない」と `kstack/no-property-destructure` と逆を向く                                                                                                        |
| `eslint/sort-imports`・`sort-keys`・`no-duplicate-imports`                                                                      | 並び順と import の書き方は formatter と `import type` の分け方に任せる                                                                                                                                                                                                                                      |
| `no-console`・`no-empty-function`                                                                                               | CLI の出力や no-op の callback を書けなくする                                                                                                                                                                                                                                                               |
| `no-continue`・`one-var`                                                                                                        | ループの早期 `continue` と、宣言を 1 文ずつ書く形を書けなくする                                                                                                                                                                                                                                             |

extends した設定の `"off"` は、利用側が `categories` を書き直しても優先される。

### kstack-layerd-architecture（`layerdArchitecture`）

6 規約すべてを載せる。「use case の処理は step 番号付きの doc と step コメントで書く」は、`kstack/use-case-steps` の messageId ごとに 3 行に分けて載せる。`kstack/use-case-steps` は、class 名が `UseCase` で終わり、本体を持つ `execute` を持つ class だけを見る。

| 規約                                                                       | ルール / 表せない理由                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 層のファイルは class で書き、モジュール直下に関数を置かない                | 表せない。ファイルが client / repository / use case の層かはディレクトリ構成で決まり、1 ファイルの AST からは決まらない。モジュール直下の関数が class 専用か複数ファイルで使うものか（private method にするか utils に移すか）も構文から区別できない                                                                                                          |
| client は外部サービスとの境界を閉じる                                      | 表せない。引数が API key・認証情報か、公開 method が endpoint と 1 対 1 かは構文から決まらない                                                                                                                                                                                                                                                                |
| repository は 1 table 1 class、1 query 1 method                            | 表せない。1 つの method が発行する query の数と、join する repository の名前が from・join 先の table と合うかは、drizzle などの呼び出しの意味が要り構文から決まらない                                                                                                                                                                                         |
| use case は execute だけを持ち、分岐と呼び出しだけを書く                   | 表せない。`UseCase` で終わる class の `execute` 以外の method は構文で数えられるが、本文の式が計算処理か client・repository の呼び出しかは構文から区別できない                                                                                                                                                                                                |
| `execute` の doc comment に、要約の 1 行と番号付きの step を並べる         | `kstack/use-case-steps`（messageId `missingDoc`・`missingSteps`・`missingSummary`）。doc comment が無い、`1. ...` の行が無い、番号付き step の前に要約行が無い形を指す。class 名が `UseCase` で終わらない use case、宣言だけの `execute` は検出しない                                                                                                         |
| 本文の各 step の先頭に、doc と同じ番号・同じ文言で `// Step N: ...` を書く | `kstack/use-case-steps`（messageId `mismatch`・`missingBodyStep`）。doc に無い番号の step コメント、文言の違う step コメント、本文に無い doc の step を指す。文言は trim 後の完全一致で見る。旧表記の `// step1:` と、`// Step1:` のように空白の無い形は step コメントとして見ない（doc の step があれば `missingBodyStep` になる）。番号の順序・連番は見ない |
| step の間を空行で区切る                                                    | `kstack/use-case-steps`（messageId `missingBlankLine`）。2 つ目以降の step コメントの直前の行が空行でない形を指す。1 つ目の step は本体の先頭に来るので要求しない                                                                                                                                                                                             |
| service・utils・libs は最後の手段                                          | 表せない。service を作る前の user の承認は agent の作業手順で、utils が複数ファイルで使われるか・ビジネスロジックを持たないかは構文から決まらない                                                                                                                                                                                                             |

### kstack-react（`react`）

全規約を載せる。構文で検出できる範囲と、情報源・責務・ファイル構成の判断が要る範囲を分ける。

| データ取得は TanStack Query の `useQuery`、props・state の派生値は render 中の計算、操作起点の処理はイベントハンドラにする                                        | `react-doctor/no-fetch-in-effect`・`no-derived-state-effect`・`no-event-handler` が目的別の誤用を部分検出する。どの目的の処理かは意味の判断が要る                                                                                                                                                                                                                   |

| Relational Queries では drizzle-orm から演算子を import しない                                     | 表せない。`no-restricted-imports` で `drizzle-orm` の `eq`・`and` を禁止すると、schema と client を持つ DB package やクエリビルダー（`db.select()`）での正しい import も指す。`db.query.<table>` の `where` に渡すかは import の時点で決まらない |

| テストでは drizzle の client を in-memory DB に差し替える                                          | 表せない。`drizzle(process.env.DATABASE_URL)` がテスト用かアプリ用か、テストが外部の DB と seed スクリプトに依存するかは構文から決まらない                                                                                                       |
