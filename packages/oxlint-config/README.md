# @taiki-kuraishi/oxlint-config

SKILL の規約を表す oxlint の共有設定と、自作ルールの JS plugin。

## 責務

- 実装すること: kstack の SKILL ごとの oxlint 共有設定（`extends` に渡す設定オブジェクト）と、既存ルールで表せない規約の自作ルール（JS plugin）
- 実装しないこと: oxfmt の設定、SKILL に書かれていない規約、型情報を使うルール（oxlint の JS plugin は型情報を使えない）

## SKILL と設定の対応

export する設定は SKILL の名前から `kstack-` を除いた名前にする（`kstack-tanstack-query` → `tanstackQuery`）。既存ルールで表せない規約は、`src/rules/` に自作ルールを置き、plugin `kstack`（`@taiki-kuraishi/oxlint-config/plugin`）から export する。表せない規約は、lint で守れないのでレビューで確かめる。

### kstack-typescript（`typescript`）

| 規約                                                           | ルール / 表せない理由                                                                                                                                                         |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 導出できる型を手書きしない                                     | `kstack/no-explicit-return-type`。type predicate・`asserts` は除く。導出できない再帰関数は disable コメントで理由を残す。戻り値のためだけの `interface` / `type` は検出しない |
| else・三項演算子を使わない。早期 return する                   | `kstack/no-else`、`no-ternary`                                                                                                                                                |
| `if` の前には空行を置く                                        | `kstack/blank-line-before-if`                                                                                                                                                 |
| 関数の引数はオブジェクトに構造化する                           | `kstack/object-params`。呼び出しの引数にその場で書く関数（コールバック）と `this` 引数は除く。名前を付けて参照で渡すコールバックは検出するので、disable コメントで理由を残す  |
| 条件付きオブジェクト spread を使わない                         | `kstack/no-conditional-spread`                                                                                                                                                |
| 小さすぎる処理を関数化しない                                   | 表せない。「小さい」「名前に意味がある」を構文から決められない                                                                                                                |
| 各メソッドで繰り返す依存の生成は constructor に置く            | 表せない。依存の生成と同じ関数の呼び出しを構文から区別できない                                                                                                                |
| 型の絞り込みのためだけに this のプロパティを分割代入しない     | 表せない。`const { x } = this` が絞り込みのためだけの別名か、複数のプロパティをまとめて読むためかを構文から区別できない                                                       |
| class でしか使わない関数は private method にする               | 表せない。1 つの class だけが呼ぶかは同じファイルの中なら数えられるが、定数の初期化や他の関数からの呼び出しと合わせて判断が要るので、レビューで確かめる                       |
| class・error・定数・型が同居するファイルはディレクトリに分ける | 表せない。ファイルの分け方と `index.ts` から何を export するかはディレクトリ構成の判断で、1 ファイルの AST からは決まらない                                                   |

規約ではないが、`class-methods-use-this` を `"off"` にする。利用側が `categories: { restriction: "error" }` で有効にしても、`this` を使わない private method（kstack-typescript の「class でしか使わない関数は private method にする」、kstack-layerd-architecture の「class 専用の処理は private method にする」の形）などを指させないため。extends した設定の `"off"` は利用側の `categories` より優先される。

規約ではないが、`unicorn/throw-new-error` も `"off"` にする。kstack-better-result のエラー定義 `class UserNotFoundError extends TaggedError("UserNotFoundError")<{ ... }>() {}` は、名前が `Error` で終わる関数を `new` 無しで呼ぶので、利用側が `plugins` に `unicorn` を入れて `categories: { style: "error" }` で有効にすると `TaggedError("UserNotFoundError")` が指される（oxlint の実装は `throw` の中に限らず、`Error` で終わる名前の呼び出しをすべて指す）。`TaggedError` は `new` で呼ぶものではないので、この指摘は直せない。

### kstack-layerd-architecture（`layerdArchitecture`）

6 規約すべてを載せる。「use case の処理は step 番号付きの doc と step コメントで書く」は、`kstack/use-case-steps` の messageId ごとに 3 行に分けて載せる。`kstack/use-case-steps` は、class 名が `UseCase` で終わり、本体を持つ `execute` を持つ class だけを見る。

| 規約                                                                       | ルール / 表せない理由                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 層のファイルは class で書き、モジュール直下に関数を置かない                | 表せない。ファイルが client / repository / use case の層かはディレクトリ構成で決まり、1 ファイルの AST からは決まらない。モジュール直下の関数が class 専用か複数ファイルで使うものか（private method にするか utils に移すか）も構文から区別できない                                                                                                          |
| client は外部サービスとの境界を閉じる                                      | 表せない。引数が API key・認証情報か、公開 method が endpoint と 1 対 1 かは構文から決まらない                                                                                                                                                                                                                                                                |
| repository は 1 table 1 class、1 query 1 method                            | 表せない。1 つの method が発行する query の数と、join する repository の名前が from・join 先の table と合うかは、drizzle などの呼び出しの意味が要り構文から決まらない                                                                                                                                                                                         |
| use case は execute だけを持ち、分岐と呼び出しだけを書く                   | 表せない。`UseCase` で終わる class の `execute` 以外の method は構文で数えられるが、本文の式が計算処理か client・repository の呼び出しかは構文から区別できない                                                                                                                                                                                                |
| `execute` の doc comment に、要約の 1 行と番号付きの step を並べる         | `kstack/use-case-steps`（messageId `missingDoc`・`missingSteps`・`missingSummary`）。doc comment が無い、`1. ...` の行が無い、番号付き step の前に要約行が無い形を指す。class 名が `UseCase` で終わらない use case、宣言だけの `execute` は検出しない                                                                                                         |
| 本文の各 step の先頭に、doc と同じ番号・同じ文言で `// Step N: ...` を書く | `kstack/use-case-steps`（messageId `mismatch`・`missingBodyStep`）。doc に無い番号の step コメント、文言の違う step コメント、本文に無い doc の step を指す。文言は trim 後の完全一致で見る。旧表記の `// step1:` と、`// Step1:` のように空白の無い形は step コメントとして見ない（doc の step があれば `missingBodyStep` になる）。番号の順序・連番は見ない |
| step の間を空行で区切る                                                    | `kstack/use-case-steps`（messageId `missingBlankLine`）。2 つ目以降の step コメントの直前の行が空行でない形を指す。1 つ目の step は本体の先頭に来るので要求しない                                                                                                                                                                                             |
| service・utils・libs は最後の手段                                          | 表せない。service を作る前の user の承認は agent の作業手順で、utils が複数ファイルで使われるか・ビジネスロジックを持たないかは構文から決まらない                                                                                                                                                                                                             |

| 行われないことを assert しない                                                           | 表せない。空・0 回・`.not` の assert が「起きないこと」か「結果が空であること」（検索結果が 0 件など）かを構文から区別できない。`expect(...).not.toHaveBeenCalled()`・`toStrictEqual([])` などを指す試作は Bad を指したが、結果として空を確かめる assert も指すので作らない。`jest`・`vitest` plugin の `no-restricted-matchers` は `bun:test` から import したテストで指摘が 0 件になり、引数を見ないので `toHaveBeenCalledTimes(1)` も指す                                                                                                                                                                                                                                                                                                                                                                                                             |
| テスト名は `it` / `test` を日本語、`describe` を英語で書く（VRT の `test` は除く）       | `vitest/valid-title`。`mustMatch` で `it` / `test` にひらがな・カタカナ・漢字を 1 文字以上要求し、`mustNotMatch` で `describe` にその文字を禁止する。`vitest`・`vite-plus/test` から import したテストと、別名 import・`.each`・`.skip`・`.only`・`.todo` を指す。`@playwright/test` から import した VRT の `test` は指さない（実測 0 件）ので、VRT の命名は `playwright` 設定の `kstack/vrt-test-name` が受け持つ。`bun:test`・`node:test` から import したテストは指摘が 0 件になる（`jest` plugin でも同じ）。式を含む template literal と変数のタイトルは検出しない。日本語を 1 文字含めば通るので、`returns 結果` のような混在は `it` / `test` では検出しない。`valid-title` の既定の検査のうち、前後の空白と文字列でないタイトルは option で切るが、空のタイトルと `describe("describe 検索")` のようなブロック名の重複は option で切れず指される |

規約ではないが、`plugins` に `vitest` を入れると有効になる `vitest` の correctness の既定ルール（`expect-expect`・`no-focused-tests` など 16 個）を `"off"` にする。`testing` を足しても、日本語名のテストに `valid-title` 以外の指摘が増えないようにするため。extends した設定の `"off"` は利用側の `categories` より優先されるので、これらのルールを使う利用側は自分の `rules` に書いて有効にする。

### kstack-drizzle-orm

3 規約すべてを載せる。「親を消すときの子の行は、外部キーの onDelete で DB に消させる」は 3 行に分けて載せる。設定は作らない。

| 規約                                                                                               | ルール / 表せない理由                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Relational Queries では drizzle-orm から演算子を import しない                                     | 表せない。`no-restricted-imports` で `drizzle-orm` の `eq`・`and` を禁止すると、schema と client を持つ DB package やクエリビルダー（`db.select()`）での正しい import も指す。`db.query.<table>` の `where` に渡すかは import の時点で決まらない |

| テストでは drizzle の client を in-memory DB に差し替える                                          | 表せない。`drizzle(process.env.DATABASE_URL)` がテスト用かアプリ用か、テストが外部の DB と seed スクリプトに依存するかは構文から決まらない                                                                                                       |
