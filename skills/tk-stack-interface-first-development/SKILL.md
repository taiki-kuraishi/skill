# tk-stack-interface-first-development

複数フェーズに分かれる大規模な実装で、root session は実装せず、フェーズの分け方とフェーズ間のつなぎ目だけを user と決める。実装は、user が開く別 session（子）に引き継ぎ prompt で渡す。合意はチャットで取り、設計書の file は作らない。子が読むのは引き継ぎ prompt だけなので、決めたことはそこに書く。

root は repo 本体の checkout（linked worktree ではない）の default branch で起動する。root はコードを書かず commit もしないので、自分の branch は要らない。herdr で委任するとき、子 workspace を root の workspace の下に開けるのも repo 本体の workspace だけ。複数の機能を並列に進めるときは、repo 本体の workspace に tab を足して root を起動し、同じ checkout を共有する（root は branch を切り替えない）。

## 手順

1. **要件を固める** — root が repo 本体の checkout の default branch にいること（`git rev-parse --show-toplevel` が `git worktree list` の 1 行目の path で、`git branch --show-current` が default branch）を確かめ、違えば、そこで起動し直すよう user に伝えて止まる。依頼と既存コードを読み、作るもの（画面・endpoint・データ・設定など）、使える既存のもの、ファイル配置の規約をつかむ。調査が広ければ subagent に任せ、root の context は設計に残す。設計が分かれる要件は user に聞き、小さな判断は仮置きして「決めてほしいこと」に入れる。完了条件: 作るものと対象外が決まっている
2. **フェーズ案を作る** — 下の「フェーズ案」の形で組む。完了条件: 次をすべて満たす
   - どのファイルも、1 つのフェーズだけが担当する
   - つなぎ目ごとに、作るフェーズと使うフェーズがあり、作るフェーズが使うフェーズの前提に入っている
   - 50 行以内に収まっている
3. **規約と今の実装に合わせる** — user に示す前に毎回、`tk-stack-skill-review` を使う subagent と `tk-stack-drift-review` を使う subagent に、並行してフェーズ案をレビューさせ、指摘は root が案に反映する（subagent には書き換えさせない）。規約から外れた配置やつなぎ目、今のコードや文書と食い違う案のまま引き継ぐと、案に合わせる契約の子はそれを直せず、並列の子が同じズレを写す。subagent には、フェーズ案の全文（設計書として扱わせる）と repo の絶対 path と次の読み方を渡す。完了条件: 指摘がすべて「直した」か「直さない（理由付き）」に分かれ、案が手順 2 の完了条件を満たしている
   - skill-review: 担当のファイルを、つなぎ目の型・API と画面を持つコードとみなして、適用する SKILL を選ぶ
   - skill-review: フェーズの中の作りは子に任せていて案に無いので、関数の本体の書き方の規約（使う hook、state の持ち方、validator、クエリの書き方、テストの組み立て）は適用外にする。その種の指摘は、子が担当ファイルを skill-review に通すときに当たるので、案には書かない
   - skill-review: 型・項目の名前は日本語で書いた子との契約なので、命名の規約の違反にしない。識別子は子が repo の命名規約で決める（ファイルの path には命名の規約を当てる）
   - drift-review: 案が既存として挙げるものと、変更する担当のファイルを今のコードと突き合わせる。案どおりに実装すると古くなる文書は、どのフェーズの担当にも入っていないものだけを指摘にする（入っていれば担当のフェーズが直す）
   - どちらも、user の指摘を反映して繰り返す時は、前回のレビュー以降に変えた部分だけを対象にする
4. **合意する** — フェーズ案をチャットに示す。あわせて、手順 3 で直した指摘と、直さなかった指摘・要確認・SKILL 同士の食い違い（理由付き）を短く示して止まる。指摘は案に反映し、手順 3 から繰り返す。完了条件: user が承認し、決めてほしいことの結論がすべて出ている
5. **引き継ぐ** — フェーズごとに引き継ぎ prompt を出し、並列に始めてよいフェーズの組と順序（例: `1 → 2 と 3 を並列 → 4`）を添える。herdr の中（`HERDR_ENV=1`）なら、続けて `skill://tk-stack-handoff` に従い、root が子を起動して質問に答え、フェーズごとの PR を merge まで進める。それ以外は root の作業はここで終わる

## フェーズ案

チャットに書くのは、次の 4 つ。user が 1 画面で読み切れる量（50 行以内）にする。

1. **目的と対象外** — 各 1〜2 行。機能には英小文字と `-` の短い名前も付ける（`tk-stack-handoff` の `<feature>`）
2. **フェーズの表と順序** — 名前・ゴール・担当・前提・完了条件。名前は英小文字と `-` の短い語で、`tk-stack-handoff` の `p<N>-<名前>` になる。フェーズを分けた理由は、順序の行に 1 行で添える。画面を作るフェーズの成功と失敗で起きることは、表の下に 1 行で書く
3. **つなぎ目** — あるフェーズが作り、別のフェーズが使う形。共有の型、API の request と status ごとの response、別のフェーズの component に渡す値、CI なら job 名や設定のキーなど。末尾に「N が作り、M が使う」を付ける
4. **決めてほしいこと** — user の判断が要るもの。新しい table、外部サービス、権限、仮置きの値など

```md
# メンバー招待（invite）

project の owner が、メールで member を招待できるようにする。対象外: 招待の取り消しと期限切れ。

1 → 2 と 3 を並列 → 4。2 と 3 は 1 の型だけが前提なので、並列にできる。

| N | 名前  | ゴール               | 担当                          | 前提 | 完了条件                |
| - | ----- | -------------------- | ----------------------------- | ---- | ----------------------- |
| 1 | types | 共有の型がある       | shared/invitation.ts          | —    | 型チェックが通る        |
| 2 | api   | 招待 API が動く      | api/ の招待 API 一式          | 1    | use case のテストが通る |
| 3 | form  | 招待フォームが描ける | web/components/InviteForm.tsx | 1    | 描画テストが通る        |
| 4 | page  | 画面から招待できる   | web/routes/members.tsx        | 2, 3 | 画面のテストが通る      |

4 の画面: 成功でフォームを空にし、409 は「既に member」と出す。

つなぎ目

- 招待 = `{ ID, プロジェクト ID, メール, 役割, 作成日時 }`（1 が作り、2・3・4 が使う）
- POST /api/projects/:projectId/invitations（2 が作り、4 が呼ぶ）
  - 認証: project の owner だけ。request: `{ メール, 役割 }`
  - response: 201 `{ 招待 }` / 403 owner ではない / 409 既に member か、招待済み

決めてほしいこと

- 招待の table を新しく作る — 仮置き: unique は (プロジェクト ID, メール)
- 招待メールの文面 — 仮置き: 固定文
```

```text
Bad: フェーズの中で閉じる関数まで並べる。子が決められることを user が読み、決めてほしいことが埋もれる
招待を作る(プロジェクト ID, メール, 役割) → 招待。失敗: 既に member, DB, メール送信
├── メンバーをメールで探す(プロジェクト ID, メール) → メンバー?
├── 招待を保存する(招待) → 招待
└── メールを送る(宛先, 件名, 本文)

Good: フェーズをまたぐ形だけ書く。上の「つなぎ目」の 2 項目で足りる
```

なぜ: 子どうしが食い違うのは、フェーズの境目だけ。フェーズの中の関数やファイルの分け方は、子が repo を見て決められる。後のフェーズの子は、前のフェーズが作ったコードの名前をそのまま使う。書く量が増えるほど、user が確かめたい決定が埋もれる。設計書を別に作らないのは、子が読むのが引き継ぎ prompt だけで、同じ内容を 2 か所に持つと、直したときに片方が古くなるから。

### 書き方

- 1 文では 1 つのことを言い切る。補足は別の文にする
- 理由は、判断を左右するものだけを 1 文で書く。長くなるなら「決めてほしいこと」にして user に聞く
- 標準の表・箇条書き・コードの形で書く。凡例が要る記号は使わない
- 表のセルは 1 行（30 字目安）に収める。ゴールは「招待 API が動く」のような言い切りの短い句にし、長くなる説明は表の下に 1 行で書く
- 決めてほしいことは 1 項目 1 行（60 字以内）にし、「何を — 仮置き: 短い値」の形で書く。項目に理由は付けず、user に聞かれたときに答える
- 関数・component・型・項目の名前は日本語で書く。endpoint とファイルの path はそのまま書く
- repo のコードや設定を読めば分かることは、書かずに子に読ませる

なぜ: user が読み切れない案は、確かめられないまま承認され、ずれが子の実装まで残る。

## フェーズの分け方

1 ファイルは 1 フェーズだけが担当する。担当はディレクトリで書き、2 つのフェーズが触りうるファイル（登録用の index、package.json、lock file など）だけファイル名で決める。前提はつなぎ目で決め、使う側は作る側のフェーズが終わってから始める。並列のフェーズどうしは使い合わない。UI は、受け取った値だけで描く表示 component と、API を呼んで渡す接続に分ける。表示 component は使う型だけを前提に API と並列に作り（props は API の response の形に合わせ、接続がそのまま渡せるようにする）、接続はその両方が終わってから作る。1 フェーズは 1 session で終わる大きさにし、確かめられる完了条件を付ける。仕事全体が 1 session に収まるなら、分けずに 1 フェーズにする。ただし、先に merge して確かめたい順序があるときは、その境目で分ける。

```text
Bad: 2 つのフェーズが api/routes/index.ts を持ち、UI 全体が API を待って直列になる
1 API — api/routes/invitations.ts, api/routes/index.ts
2 UI  — web/routes/members.tsx, api/routes/index.ts（前提 1）

Good: index は API のフェーズだけが持ち、表示は型だけを前提に API と並列にする（上の表）
```

なぜ: 並列の子が同じファイルを触ると、片方の変更が上書きされるか merge で衝突する。使う先がまだ無いフェーズは型チェックが通らず、完了を確かめられない。大きすぎるフェーズは子の context を使い切り、途中で前提を落とす。小さい仕事を分けると、session の起動と PR の手間が、仕事そのものより大きくなる。

## 引き継ぎ prompt

フェーズごとに次の形で出す。子は会話の履歴を持たず、読むのはこの prompt だけ。担当にかかるつなぎ目と決めたことは、案から全文を貼る。

```md
フェーズ N（<名前>）を実装してください。目的: <機能の 1 行>。ほかのフェーズ（<N 名前: ゴール>, …）は別の session が担当します。

- 担当: <ファイル・ディレクトリ>。触るのはここだけ
- つなぎ目（user と合意済み。この形に合わせる）: <フェーズ N が作る・使うつなぎ目>
- 決めたこと: <フェーズ N にかかる「決めてほしいこと」の結論。仮置きは「仮置き」と書く>
- 名前は日本語で書いてある。識別子と型の書き方は repo の規約で決める（つなぎ目は形が一致すればよい）。前提フェーズで作られたものと既存のものは、コードにある名前をそのまま使う。フェーズの中の関数やファイルの分け方は自由に決めてよい
- つなぎ目のとおりでは実装できない、または担当外のファイルを変える必要が出たら、そこで止めて理由と変更案を報告する
- 完了条件: <フェーズの完了条件>
- 完了条件を満たしたら、報告の前に `tk-stack-skill-review` を使う subagent と `tk-stack-drift-review` を使う subagent に、並行して担当ファイルだけをレビューさせる。drift-review にはつなぎ目の全文も渡す（ほかのフェーズの担当ファイルはまだ無くてよい）。subagent には直させず、指摘はあなたが直し、直した後も完了条件を満たすことを確かめる。つなぎ目か担当外のファイルを変えないと直せない指摘は、直さずに報告する
- 最後に、変更したファイル・完了条件の確認結果・skill-review と drift-review で直した指摘と直さなかった指摘（理由付き）・つなぎ目との差分を報告する。commit はしない
```

子に止めて報告させるのは、他の子が同じつなぎ目を前提に並列で進んでいるから。つなぎ目から来る規約の指摘を子に直させないのも同じ理由で、直すかどうかは root が決める。skill-review と drift-review の指示を prompt に書くのは、子がこの SKILL を読まないから。user がその報告を root に持ってきたら（tk-stack-handoff で委任したなら、子から intercom で直接届く）、root がつなぎ目を直して手順 3 を通し、影響するフェーズの引き継ぎ prompt を出し直す。
