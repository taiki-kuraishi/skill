# kstack-interface-first-development

複数フェーズに分かれる大規模な実装で、root session は実装せず、次に始めるフェーズの分け方とフェーズ間のつなぎ目を user と決める。実装は別 session（子）に引き継ぎ prompt で渡すが、起動方式によらず root が質問・進捗・完了報告を受け、user review の窓口を最後まで持つ。合意はチャットで取り、設計書の file は作らない。子が読むのは引き継ぎ prompt だけなので、決めたことと root への連絡先はそこに書く。

フェーズは最初に全部は決めない。最初に作るのは、この session でやることの一覧だけ。フェーズは、前のフェーズが merge されるたびに、その一覧から次の回の分だけを切り出す。

root は repo 本体の checkout（linked worktree ではない）の default branch で起動する。root はコードを書かず commit もしないので、自分の branch は要らない。herdr で委任するとき、子 workspace を root の workspace の下に開けるのも repo 本体の workspace だけ。複数の機能を並列に進めるときは、repo 本体の workspace に tab を足して root を起動し、同じ checkout を共有する（root は branch を切り替えない）。

## 手順

1. **要件を固める** — root が repo 本体の checkout の default branch にいること（`git rev-parse --show-toplevel` が `git worktree list` の 1 行目の path で、`git branch --show-current` が default branch）を確かめ、違えば、そこで起動し直すよう user に伝えて止まる。依頼と既存コードを読み、作るもの（画面・endpoint・データ・設定など）、使える既存のもの、ファイル配置の規約をつかむ。調査が広ければ subagent に任せ、root の context は設計に残す。設計が分かれる要件は user に聞く。そのうえで、完了条件を満たすためにこの session でやらなければならないことを 1 項目 1 行の一覧にし、todo に書く（compaction の後も残る）。小さな判断は、仮置きの値を添えて項目に書き留め、効くフェーズの案で「決めてほしいこと」に入れる。フェーズの分け方と各項目の設計は、ここでは決めない。完了条件: 作るものと対象外が決まり、やることの一覧がある
2. **次のフェーズ案を作る** — 前のフェーズが merge 済みなら、root の checkout を、`git fetch` して `merge --ff-only` で default branch の最新に進め（herdr で委任したなら `kstack-handoff` の統合で済んでいる）、そのコードと結果に合わせて一覧を直す。一覧から、下の「フェーズの分け方」で今回のフェーズだけを切り出し、下の「フェーズ案」の形で組む。完了条件: 次をすべて満たす
   - 今回のどのフェーズも、前提がすべて merge 済みである
   - 今回のどのファイルも、1 つのフェーズだけが担当する
   - つなぎ目ごとに、作るフェーズ（今回の中）と、使う仕事（一覧の項目）が書かれている
   - 50 行以内に収まっている
3. **規約と今の実装に合わせる** — フェーズ案を user に初めて示す前に 1 回だけ、`kstack-skill-review` を使う subagent と `kstack-drift-review` を使う subagent に、並行してフェーズ案をレビューさせ、指摘は root が案に反映する（subagent には書き換えさせない）。規約から外れた配置やつなぎ目、今のコードや文書と食い違う案のまま引き継ぐと、案に合わせる契約の子はそれを直せず、並列の子が同じズレを写す。subagent には、フェーズ案の全文（設計書として扱わせる）と repo の絶対 path と次の読み方を渡す。完了条件: 指摘がすべて「直した」か「直さない（理由付き）」に分かれ、案が手順 2 の完了条件を満たしている
   - skill-review: 担当のファイルを、つなぎ目の型・API と画面を持つコードとみなして、適用する SKILL を選ぶ
   - skill-review: フェーズの中の作りは子に任せていて案に無いので、関数の本体の書き方の規約（使う hook、state の持ち方、validator、クエリの書き方、テストの組み立て）は適用外にする。その種の指摘は、子が担当ファイルを skill-review に通すときに当たるので、案には書かない
   - skill-review: 型・項目の名前は日本語で書いた子との契約なので、命名の規約の違反にしない。識別子は子が repo の命名規約で決める（ファイルの path には命名の規約を当てる）
   - drift-review: 案が既存として挙げるものと、変更する担当のファイルを今のコードと突き合わせる。案どおりに実装すると古くなる文書は、今回のどのフェーズの担当にも入っていないものだけを指摘にする（入っていれば担当のフェーズが直す。後のフェーズで直すと決めたものは、一覧に足す）
4. **合意する** — フェーズ案をチャットに示す。あわせて、手順 3 で直した指摘と、直さなかった指摘・要確認・SKILL 同士の食い違い（理由付き）を短く示す。「決めてほしいこと」は、案を示した同じ turn で質問 tool（omp なら `ask`、選択肢に仮置きを recommended として入れる）にまとめて渡し、回答を受け取ってから先へ進む。質問 tool が無い環境だけ、チャットに 1 項目ずつ聞く。user の指摘と回答は案に反映して示し直す。手順 3 のレビューは回し直さず、手順 2 の完了条件を満たすことは root が確かめる。完了条件: user が承認し、決めてほしいことの結論がすべて出ている

   ```text
   Bad: 決めてほしいことをチャットに並べて turn を終え、次の turn で「まだ回答いただけていません」と催促する
   Good: 案を示し、決めてほしいことを ask tool の questions に 1 項目 1 問で渡し、全問の回答を受け取って案に反映する
   ```

   なぜ: チャットに並べた問いは、user が一部にしか答えなくても turn が進み、答えの漏れと催促が往復を増やす。質問 tool なら全問に答えるまで先へ進まない。

5. **引き継いで監督する** — 切り出した項目はフェーズごとの todo に置き換える。root の `intercom({ action: "status" })` が `Connected: Yes` であることを確かめ、`Session ID` を控える。接続できなければ root で user に必要な設定を伝えて止まり、子へ窓口を移さない。今回のフェーズだけを、作業場所と root の連絡先を埋めた引き継ぎ prompt で始め、フェーズが複数なら並列に始めると添える。herdr の中（`HERDR_ENV=1`）なら、`skill://kstack-handoff` で子を起動し、質問・user review・PR の merge まで root が管理する。それ以外は「[手動で引き継ぐ](references/manual-handoff.md)」に従い、user が子を起動した後も root が報告と質問を受け、`skill://kstack-review-request` で user review を依頼する。子の状況は root が確認し、user に子の pane の巡回や報告の転送を頼まない。子から既存パターンから外れる実装の承認を求められたら、root は自分で決めずに user に聞き、結論を子に返す。今回のフェーズがすべて merge されたら、一覧に残りがあれば手順 2 に戻り、無ければ終わる。完了条件: 今回のフェーズの承認と明示許可された統合が確認できている。許可待ち・未統合のフェーズがあれば root に待ちの状態を残す

## フェーズ案

チャットに書くのは、次の 5 つ。今回のフェーズだけを書き、user が 1 画面で読み切れる量（50 行以内）にする。

1. **目的と対象外** — 各 1〜2 行。機能には英小文字と `-` の短い名前も付ける（`kstack-handoff` の `<feature>`）。2 回目以降も同じ名前を使う
2. **やること** — 完了条件を満たすために残っている仕事を 1 項目 1 行で書き、merge 済みの項目は「済」、今回のフェーズに入る項目はその N を添える。後の仕事は、フェーズに分けず、始められる条件だけを添える
3. **フェーズの表と順序** — 今回のフェーズの名前・ゴール・担当・前提・完了条件。名前は英小文字と `-` の短い語で、`kstack-handoff` の `p<N>-<名前>` になる。N は前の回から続ける。フェーズを分けた理由は、順序の行に 1 行で添える。画面を作るフェーズの成功と失敗で起きることは、表の下に 1 行で書く
4. **つなぎ目** — 今回のフェーズが作り、後の仕事が使う形。共有の型、API の request と status ごとの response、別のフェーズの component に渡す値、CI なら job 名や設定のキーなど。末尾に「N が作り、<一覧の項目> が使う」を付ける
5. **決めてほしいこと** — user の判断が要るもの。新しい table、外部サービス、権限、仮置きの値、案の段階で分かる既存パターンから外れる実装（引き継ぎ prompt に挙げたもの）など

```md
# メンバー招待（invite）

project の owner が、メールで member を招待できるようにする。対象外: 招待の取り消しと期限切れ。

やること

- 招待の型を作る（1 済）
- 招待 API を作る（2）
- 招待フォームを作る（3）
- メンバー画面から招待できるようにする（2 と 3 の後）

2 と 3 を並列に始める。どちらも 1 が作った型だけが前提なので、並列にできる。

| N | 名前 | ゴール               | 担当                          | 前提 | 完了条件                |
| - | ---- | -------------------- | ----------------------------- | ---- | ----------------------- |
| 2 | api  | 招待 API が動く      | api/ の招待 API 一式          | 1    | use case のテストが通る |
| 3 | form | 招待フォームが描ける | web/components/InviteForm.tsx | 1    | 描画テストが通る        |

3 のフォーム: 送信中は送信を押せず、エラーの文言を受け取って出す。

つなぎ目

- POST /api/projects/:projectId/invitations（2 が作り、メンバー画面が呼ぶ）
  - 認証: project の owner だけ。request: `{ メール, 役割 }`
  - response: 201 `{ 招待 }` / 403 owner ではない / 409 既に member か、招待済み
- フォームに渡す値 = `{ 送信中, エラー, 送信する }`（3 が作り、メンバー画面が渡す）

決めてほしいこと

- 招待の table を新しく作る — 仮置き: unique は (プロジェクト ID, メール)
- 招待メールの文面 — 仮置き: 固定文
```

```text
Bad: フェーズの中で閉じる関数まで並べる。子が決められることを user が読み、決めてほしいことが埋もれる
招待を作る(プロジェクト ID, メール, 役割) → 招待。失敗: 既に member, DB, メール送信
├── メンバーをメールで探す(プロジェクト ID, メール) → メンバー?
├── 招待を保存する(招待) → 招待
└── メールを送る(宛先, 件名, 本文)

Good: フェーズをまたぐ形だけ書く。上の「つなぎ目」の 2 項目で足りる
```

なぜ: 子どうしが食い違うのは、フェーズの境目だけ。フェーズの中の関数やファイルの分け方は、子が repo を見て決められる。後のフェーズの子は、前のフェーズが作ったコードの名前をそのまま使う。書く量が増えるほど、user が確かめたい決定が埋もれる。設計書を別に作らないのは、子が読むのが引き継ぎ prompt だけで、同じ内容を 2 か所に持つと、直したときに片方が古くなるから。

### 書き方

- 1 文では 1 つのことを言い切る。補足は別の文にする
- 理由は、判断を左右するものだけを 1 文で書く。長くなるなら「決めてほしいこと」にして user に聞く
- 標準の表・箇条書き・コードの形で書く。凡例が要る記号は使わない
- 表のセルは 1 行（30 字目安）に収める。ゴールは「招待 API が動く」のような言い切りの短い句にし、長くなる説明は表の下に 1 行で書く
- 決めてほしいことは 1 項目 1 行（60 字以内）にし、「何を — 仮置き: 短い値」の形で書く。項目に理由は付けず、user に聞かれたときに答える
- 関数・component・型・項目の名前は日本語で書く。endpoint とファイルの path はそのまま書く
- repo のコードや設定を読めば分かることは、書かずに子に読ませる

なぜ: user が読み切れない案は、確かめられないまま承認され、ずれが子の実装まで残る。

## フェーズの分け方

今始められる仕事（前提がすべて merge 済みの仕事）だけをフェーズにする。後の仕事は、前のフェーズが merge されてから、そのコードを見て切り出す。今始められる仕事が複数あれば、同じ回の並列のフェーズにしてよい。1 ファイルは 1 フェーズだけが担当する。担当はディレクトリで書き、2 つのフェーズが触りうるファイル（登録用の index、package.json、lock file など）だけファイル名で決める。前提はつなぎ目で決め、使う側は作る側のフェーズが merge されてから切り出す。並列のフェーズどうしは使い合わない。UI は、受け取った値だけで描く表示 component と、API を呼んで渡す接続に分ける。表示 component は使う型だけを前提に API と並列に作り（props は API の response の形に合わせ、接続がそのまま渡せるようにする）、接続はその両方が merge されてから切り出す。1 フェーズは 1 session で終わる大きさにし、確かめられる完了条件を付ける。仕事全体が 1 session に収まるなら、分けずに 1 フェーズにする。ただし、先に merge して確かめたい順序があるときは、その境目で分ける。

```text
Bad: UI 全体を API の後の回に回し、表示まで API を待って直列になる
回 1: 1 API — api/routes/invitations.ts, api/routes/index.ts
回 2: 2 UI  — web/routes/members.tsx（前提 1）

Good: 表示は型だけを前提に API と同じ回で並列にし、接続だけを後の回に回す。index は API のフェーズだけが持つ（上の表）
```

なぜ: 前提が終わっていない仕事を先にフェーズにすると、前のフェーズの実装で状況が変わったとき、案が古くなる。並列の子が同じファイルを触ると、片方の変更が上書きされるか merge で衝突する。使う先がまだ無いフェーズは型チェックが通らず、完了を確かめられない。大きすぎるフェーズは子の context を使い切り、途中で前提を落とす。小さい仕事を分けると、session の起動と PR の手間が、仕事そのものより大きくなる。

## 引き継ぎ prompt

フェーズごとに次の形で出す。子は会話の履歴を持たず、読むのはこの prompt だけ。作業場所・branch・root の full Session ID を起動前に埋め、担当にかかるつなぎ目と決めたことは案から全文を貼る。同じ回のほかのフェーズが無ければ、それを書いた 1 文は外す。

```md
フェーズ N（<名前>）を実装してください。目的: <機能の 1 行>。同じ回のほかのフェーズ（<N 名前: ゴール>, …）は別の session が担当します。

- 作業場所: `<worktree の path>`（branch `<branch>`）。repo の変更はこの worktree の中だけにする
- root の連絡先: `<root の full Session ID>`。この session は子で、user との会話と user review の窓口は root が持つ
- 開始: `intercom({ action: "status" })` が `Connected: Yes` であることを確かめ、自分の full Session ID とフェーズ N・cwd・branch を `intercom({ action: "send", to: "<root の full Session ID>", message })` で root に報告する。連絡先が未指定、接続できない、送信できない場合は実装を始めず、子が user review の窓口になる代替には切り替えない
- 質問: 依頼文だけでは決められないことは `intercom({ action: "ask", to: "<root の full Session ID>", message })` で root に聞く。user に聞きたいことも root に聞く。ask が timeout したら turn を終えて root からの message を待つ
- 担当: <ファイル・ディレクトリ>。触るのはここだけ
- つなぎ目（user と合意済み。この形に合わせる）: <フェーズ N が作るつなぎ目>
- 決めたこと: <フェーズ N にかかる「決めてほしいこと」の結論。仮置きは「仮置き」と書く>
- 名前は日本語で書いてある。識別子と型の書き方は repo の規約で決める（つなぎ目は形が一致すればよい）。前提フェーズで作られたものと既存のものは、コードにある名前をそのまま使う。フェーズの中の関数やファイルの分け方は、既存パターンに倣う範囲で自由に決めてよい
- つなぎ目のとおりでは実装できない、または担当外のファイルを変える必要が出たら、そこで止め、理由と変更案を intercom の `ask` で root に報告する
- 既存の実装の拡張と言えない実装は、書く前に止め、外れる案と既存に倣う案を代償付きで intercom の `ask` で root に聞き、承認されたものだけ書く。該当するのは、この prompt で決まっていない次のもの: 新しいディレクトリの作成（既存のディレクトリの下に足すものも含む）、新しい package・レイヤー、テストの無い package・app へのテストの追加、repo に前例の無い書き方（ライブラリの内部構造への依存、新しい依存など）、規約に抵触しうる切り方（1 ファイルに複数の責務など）、既存の関数・モジュールが持つ責務の移動（採番や計算をする場所を変えるなど）。前例に倣う形の拡張（項目の追加、型の generic 化など）は含めない。完了報告で事後に知らせて済ませない
- 完了条件: <フェーズの完了条件>
- 完了条件を満たしたら、最初の報告の前に 1 回だけ、`kstack-skill-review` を使う subagent、`kstack-drift-review` を使う subagent、`ponytail-review` を使う subagent に、並行して担当ファイルだけをレビューさせる。drift-review にはつなぎ目の全文も渡す（ほかのフェーズの担当ファイルはまだ無くてよい）。`ponytail-review` が環境に入っていなければ、代わりに review せず、入っていないことを報告に書く。subagent には直させず、指摘はあなたが直し、直した後も完了条件を満たすことを確かめる。つなぎ目か担当外のファイルを変えないと直せない指摘と、ponytail-review の指摘のうち決めたことを削る・既存パターンから外れる修正になるものは、直さずに報告する。報告の後に届く review の指摘を直すときは、この 3 つのレビューを回し直さず、完了条件だけ確かめて報告する
- 最後に、フェーズ N・cwd・branch・変更したファイル・完了条件ごとの確認コマンドと結果・skill-review と drift-review と ponytail-review で直した指摘と直さなかった指摘（理由付き）・つなぎ目との差分を、intercom の `send` で root に報告して turn を終える
- user review の依頼・指摘への返信・再依頼と、review の開始・終了は root に任せ、user に直接 review を頼まない。user がこの pane で review を頼んだ場合も root に連絡して窓口をそろえる。root から届いた指摘を直して再検証し、指摘ごとの対応結果と返信文を intercom の `send` で root に返して待つ
- Git 操作は、user が明示した許可と範囲を root から受け取ったときだけ行う。許可された対象 branch と操作（commit・push・PR・merge など）を自分の worktree で実行し、commit hash・PR の merge commit などの結果を intercom の `send` で root に報告する。許可が無い間は commit しない。review の承認から Git の許可を推測しない
```
