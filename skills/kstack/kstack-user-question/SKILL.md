# kstack-user-question

user に聞くとき、確かめるとき、説明を求められて答えるときの書き方。いつ聞くか・聞かずに進むかは、読み込んだ開発フロー・mode・playbook が決める。この SKILL は聞くと決めた後の書き方だけを決める。ほかの SKILL が聞く内容の項目を決めている（`kstack-review-exemption` の差分と規約の対など）ときは、その項目を「事実」に書く。review の依頼文と PR の通知は、`kstack-review-request` と読み込んだ開発フローの形式に従う。

## 「事実 / 背景 / 質問」の 3 つに分けて書く

聞くときは、次の 3 つの見出しを付けて、この順に書く。説明を求められて答えるだけで聞くことが無いときは、「事実 / 背景」の 2 つにする。

- **事実** — 自分で確かめたことだけを書く。コード・設定・コマンドの出力・差分・URL を、その場で読める形で示す。推測は「推測:」を付けて分ける
- **背景** — なぜ今この判断が要るか、決めないと何が止まるか、自分が試したことと、その結果
- **質問** — 1 つだけ、1 文で書き、「？」で終える。選択肢があれば、各選択肢の代償を 1 行ずつ添える

```text
Bad: 「A と B のどちらにしますか？」とだけ書き、A・B が何で、なぜ今決める必要があるかを書かない
Good: 事実に A・B の実物（コード片や設定）を並べ、背景に決めないと止まる作業を書き、質問で「A と B のどちらにしますか？」と聞く
```

なぜ: user は agent が読んだファイルも、subagent とのやり取りも見ていない。事実と背景が無いと、user はまず agent に聞き返すことになり、1 往復が無駄になる。

## 用語や規約の名前は、具体例と並べて使う

SKILL の見出し、規約の名前、agent が付けた呼び名（「案 A」「mode 形式」など）を書くときは、その中身を表すコード・設定・出力の例を、同じ message に並べる。例を出せないなら、その用語を使わずに中身を書く。

```text
Bad: 「SKILL は restore と save を 1 つの action の mode で切り替えると書いているのに、例は 2 つの action に分けている」
Good: 3 つの書き方を YAML で並べ（2 つの action、key を output で渡す、1 つの action を mode で切り替える）、「SKILL が勧めているのは 3 つ目で、この例は 1 つ目を使っている」と書く
```

なぜ: 見出しや呼び名は、それを読んだ agent にしか意味が通じない。user が中身を知らない言葉で説明すると、user は判断できないまま「どういうこと？」と聞き返すことになる。

## 1 回の返答で聞くのは 1 問だけにする

答えを受け取ってから次を聞く。おすすめは根拠を書けるときだけ付け、選択肢の外の答えも受け付ける。user が一部にしか答えなかったら、答えのあった分だけで進め、残りは次の 1 問として聞き直す。

```text
Bad: 1 つの返答に、merge するか・名前をどうするか・次に何を作るかの 3 問を並べる
Good: いま作業を止めている 1 問だけを聞き、答えを受けてから次の 1 問を書く
```

なぜ: 複数を並べると、user がどれに答えたかを取り違え、答えの漏れに気づけず、後から催促することになる。

## 聞き直すときは、事実と背景から書き直す

返事が無い質問をもう一度聞くときは、前の message を参照せず、事実・背景・質問を書き直す。agent が subagent や子 session とのやり取りで決めたことも、user に見える形で事実に書いてから進める。

```text
Bad: 「先ほどの質問はいかがでしょうか」とだけ書く
Good: 何で止まっているか、これまでに決まったこと、比べる案を書き直して、同じ 1 問を聞く
```

なぜ: user は数 turn 前の質問を覚えておらず、subagent とのやり取りも読んでいない。参照だけの催促では答えられない。

## 何を作るかの承認は、中身を見せて取る

新しい SKILL・playbook・package・画面・設計を作ってよいかを聞くときは、名前と一行の説明の一覧ではなく、実物と同じ形の下書き（SKILL なら本文、playbook なら手順と完了条件、設計なら型や画面の構成）を見せる。下書きが長いときは、ファイルにして user が行ごとにコメントできる場（Crit、PR など）に出す。下書きの中で agent が決めたことは、「決めたいこと」として案と並べる。

```text
Bad: 「画面の playbook、テストの playbook を作りましょうか」と名前だけ並べて聞く
Good: 各 playbook の手順・完了条件・止まる点まで書いた下書きを Crit に出し、決めたことを案として並べて聞く
```

なぜ: 名前だけでは、user は何が決まり、何を作ることになるかを判断できない。作ってから見せると、要らない方針まで作り直しになる。

## 選択式の UI に背景を押し込まない

omp の ask tool のような選択式の UI では聞かず、チャットに書く。bot が依頼元の画面（Item の質問欄など）で聞くときは、事実と背景を本文やコメントに書き、質問欄には「質問」の 1 文と選択肢だけを置く。

```text
Bad: 選択肢のボタンだけを出し、背景はボタンの文言に詰め込む
Good: 事実と背景をコメントに書き、質問欄には「？」で終わる 1 文と選択肢を置く
```

なぜ: 選択式の UI は背景を書く場所が狭く、user は判断材料を見ないまま、用意された選択肢の中から選ぶことになる。
