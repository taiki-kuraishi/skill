# バグ修正

**持つもの: 再現から、直ったことの確認まで。**

使う場面: 期待する動きが文書・テスト・依頼・既存の挙動のどこかで決まっている不具合を直す。期待する動きから決める必要があるものは、振り分け表の「どれにも当たらない」に回す。

1. 再現する。user に再現を頼まず、テスト・script・画面の操作で同じ症状を出す（誰が実行するかは読み込んだ mode の agent の使い方に従う）。出なければ条件を絞り、ログを足して出るまで続ける。それでも出ないときは、試したことを報告して止まる。完了条件: 症状を出す手順かテストがある
2. 原因を絞る。仮説を並べ、1 回の確認で一番多くを消せるものから、ログや実行結果で確かめる。コードを読んだ推測だけで決めない。完了条件: 最初に間違えた場所（file:line）と、そこが原因だと示す実行結果がある
3. 手順 1 の再現をテストにする（置き場所と書き方は `kstack-testing`）。安く書けるテストが無ければ、再現の手順を報告に残す
4. 最小の修正をする。境界をまたぐ変更や既存パターンから外れる変更が要るなら、`kstack-playbooks` の「playbook の回し方」の手順 2 で聞く
5. 手順 1 と同じ方法で、症状が消えたことを確かめる。別の方法での確認や「たぶん直った」は確認にしない
6. commit するときは、テストを先、修正を後の 2 つに分ける

```text
Bad: 効きそうな guard を足し、既存のテストが通ったので直ったとする
Good: 症状を落ちるテストにし、原因の行を直し、同じテストが通る出力を示す
```

なぜ: 再現を自分で持たないと、直ったかを確かめる手段が無い。テストを先に commit すると、直す前は落ちていたことが履歴で分かる。

**報告**: 何が壊れていたか、原因（file:line）、直したこと、確かめ方（落ちる出力と通る出力）。
