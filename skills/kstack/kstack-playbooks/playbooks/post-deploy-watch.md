# デプロイ後に本番で確かめる

**持つもの: 変えた箇所が本番で動いているかの判定。監視は subagent、判定は root。本番は変えない。**

使う場面: merge した変更のデプロイが終わり、本番で変えた箇所が正しく動いていることを確かめたい。デプロイ・ロールバック・再実行はこの playbook に入らず、user の明示の指示があるときだけ行う。

1. 確かめる振る舞いを決める。merge した PR の差分から、変わった振る舞い（endpoint・job・画面）を挙げ、それぞれに成功のシグナル（その処理の成功ログ、2xx の件数、書かれた行）と失敗のシグナル（その処理のエラーログ、5xx）を決める。失敗のシグナルのデプロイ前の同じ長さの期間の件数を、手順 3 と同じ照会で subagent に数えさせ、比べる基準にする。完了条件: 振る舞いごとに成功と失敗のシグナルと、失敗の基準の件数がある
2. 本番に変更が入っていることを確かめる。デプロイの記録や本番の版の表示から、動いている版が merge の commit を含むかを見る。含まれていなければ監視を始めず、デプロイの記録と版を示して user に返す（デプロイはやり直さない）。完了条件: 本番の版と、それが merge の commit を含む根拠がある
3. 監視を subagent に任せる。`kstack-root-driven-development` の Subagent contract の「コマンドが要る調査」の agent に、no-edit を明示し、contract の 7 項目で頼む。依頼には、手順 1 のシグナルと基準の件数、見る間隔、終わる条件も書く。終わる条件は、全振る舞いで成功のシグナルを見たとき、失敗のシグナルが基準より増えたとき、上限の時間（依頼に無ければ 1 時間）が来たときのどれか早いもの。生のログは subagent の中に留め、件数・ログの ID・時刻だけを返させる。本番に書き込むリクエストは送らせない
4. 判定する。subagent の報告から、振る舞いごとに「確認できた」「壊れている」「確認できない（その処理が呼ばれなかった）」を root が決める。壊れていれば、根拠と、直す案かロールバックの案を user に送る。直すならバグ修正の playbook に移る

```text
Bad: デプロイが成功したことだけを見て「本番で動いています」と報告する / エラーが出たので、聞かずにロールバックする
Good: 変えた endpoint の 2xx をデプロイ後に確かめ、5xx がデプロイ前と同じ件数のままであることを示して報告する
```

なぜ: デプロイの成功は、変えた処理が本番で呼ばれて正しく動いたことを示さない。デプロイ前の件数と比べないと、前からあるエラーを今回の変更のせいにする。ロールバックも本番を変える操作なので、判定する側が聞かずに行わない。

**報告**: 本番の版、振る舞いごとの判定と根拠（件数・ログの ID・時刻、デプロイ前との比較）、確認できなかった振る舞いとその理由、壊れていたときの案。
