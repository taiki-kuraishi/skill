# テストを足す・直す

**持つもの: 既存のコードの振る舞いを守るテストが、流して通ること。コードの振る舞いは変えない。**

使う場面: 実装済みのコードにテスト（spec・VRT・E2E）を足す、または既存のテストの書き方を `kstack-testing` に合わせ直す。CI で落ちたテストは CI の失敗の playbook、不具合の再現テストはバグ修正の playbook で扱う。

1. 今あるものを掴む。対象の spec があるか、テストを流す task（`mise tasks --all`、`vite.config.ts` の `run.tasks`）、既存の spec がテストをどう起動しているかを調べる。完了条件: spec の path か「無い」と、流すコマンドが分かっている
2. 守る振る舞いを並べる。`kstack-testing` の「テストケースは正常系 1 件と、振る舞いごとに 1 件にする」に従い、validator が弾く 400 と、起きないことは除く。振る舞いの出典（依頼・文書・既存の実装）が無いものは聞く。完了条件: 日本語の `it` 名の一覧ができ、各名前に出典がある
3. 置き場所を決める。API は route 定義ファイル 1 つに spec 1 つ、ブラウザのテストは VRT と E2E のディレクトリに分ける（`kstack-playwright`）。テストの無い package にテストを足すとき、新しいディレクトリや helper を作るときは、`kstack-root-driven-development` の「既存パターンから外れる実装」として書く前に聞く。完了条件: 触るファイルが、既存の spec と helper か、承認された新しい置き場所だけになっている
4. 書く。準備と書き方は `kstack-testing`（DB は `kstack-drizzle-orm` の in-memory DB、認証は `kstack-better-auth` のテスト用 instance）に従う。テストの起動方法（`app.request` か型付き client か）は SKILL に無いので、既存の spec に合わせる
5. 流す。subagent に流させ、足したケースが通る出力を受け取る。そのあと対象のコードを一時的に壊し、足したケースが落ちることを確かめてから戻す。壊した変更は commit しない。完了条件: 足したケースが通り、壊したときは落ちた
6. 既存のテストの期待値を変える、skip する、消す必要が出たら、そこで止まって聞く。答えが「実装が誤り」なら、バグ修正の playbook に切り替える
7. テストだけを 1 つの commit にする

```text
Bad: テストが通らないので、期待値を今の実装の出力に合わせて書き換える
Good: 期待値と実装が食い違ったら、どちらが正しいかを聞く
```

なぜ: テストは振る舞いの約束である。今の出力に合わせて書くと、誤った振る舞いまで固定する。一時的に壊して落ちることを見れば、何も守らないテストを足していないと分かる。

**報告**: 足したテスト名と出典、置き場所、流した出力、壊して落ちたことの確認、聞いて決めたこと。
