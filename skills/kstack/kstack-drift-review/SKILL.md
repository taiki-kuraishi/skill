# kstack-drift-review

文書に書かれた内容を実装と突き合わせ、食い違い（ドリフト）を指摘する。人も agent も、コードを読む前に文書を信じて動く。AGENTS.md は毎回の session に読み込まれる。ずれた文書を読んだ側は、ずれた前提のまま作業する。

## 手順

1. **対象を決める** — 依頼でファイル・範囲・設計書を指定されたらそれに従う。指定がなければ未コミットの変更（`git diff HEAD` と untracked ファイル）、それも無ければ base branch との差分（`git diff <base>...HEAD`）を対象にする。repo 全体は、全体を見るよう頼まれたときだけ対象にする。完了条件: 対象（変更のファイルと変更行、設計書、または repo 全体）が確定している
2. **文書を集めて分ける** — `git ls-files` で全階層の `AGENTS.md`・`CLAUDE.md`・`README.md` と `docs/` 以下を列挙し、それらが参照する文書（`.claude/rules/*.md` など）を足す。path と冒頭を見て、各文書を「現行」か「記録」に分ける（下の「判断の目安」）。完了条件: 列挙した全文書が現行・記録のどちらかになっている
3. **現行の文書を読む** — 現行の文書を全文読む。対象が変更か設計書なら、対象が触れるファイルの祖先ディレクトリに無い `AGENTS.md`・`CLAUDE.md`・`README.md` は、対象が触れる名前（パス、関数、コマンド、環境変数、endpoint。変更前の名前も含む）で grep して、当たったものだけ読む。完了条件: 現行の文書がすべて「読んだ」か「grep で無関係」になっている
4. **主張を抜き出す** — 読んだ文書から、実装と照らして真偽を決められる記述（主張）を `文書:行` 付きで抜き出す。コマンド・script、パス・ディレクトリ構成、API（endpoint、関数、型、signature）、環境変数・設定値、依存とバージョン、処理の流れと挙動、規約（〜する・〜しない）が当たる。対象ごとの範囲は次のとおり。完了条件: 範囲の主張がすべて一覧になっている
   - 変更: 変更が触れた名前・挙動・設定についての主張と、文書の変更された行の主張
   - 設計書: 設計書のすべての主張と、設計どおりに実装すると古くなる現行の文書の主張
   - repo 全体: 現行の文書のすべての主張。規約は grep や設定で確かめられるものに絞り、絞ったことを「確認済み」に書く
5. **実装と突き合わせる** — 主張ごとにコードと設定（`package.json` の scripts、mise の tasks、CI、環境変数の定義など）を読み、「一致 / ドリフト / 要確認」を付ける。規約は、対象の実装（設計書なら、書かれたとおりに作った後の実装）が従っているかを見る。網羅を示す一覧（環境変数の表、コマンド一覧、endpoint 一覧、ディレクトリの tree）は、対象の実装にあるのに載っていないものも探す。完了条件: すべての主張に判定が付いている
6. **報告する** — 下の形式で並べる。文書もコードも書き換えず、user が修正を頼んだときだけ直す

現行の文書が多く、subagent が使える環境なら、手順 3 以降を文書単位で分担してよい。

## 報告の形式

ドリフトは文書順・行順に並べ、1 件ごとに文書の記述と実装の事実を、どちらも場所付きで示す。

```md
## ドリフト

- `README.md:14` — 「`bun run dev` で API を起動する」
  - 実装: `package.json:6` の scripts に `dev` は無く、起動は `bun run start`
  - ずれた側: 文書が古い（`dev` は `a1b2c3d` で `start` に改名された）
  - 修正案: `bun run start` に書き換える

## 要確認

- `docs/architecture.md:40` — 「認証は middleware で行う」
  - 判定できない理由: middleware と route handler の両方で session を検証している

## 既存

- `AGENTS.md:22` — 「テストは `tests/` に置く」
  - 実装: テストは対象ファイルの隣（`src/**/*.test.ts`）にある

## 確認済み

- 一致: AGENTS.md（12 件）、README.md（5 件）、docs/api.md（8 件）
- grep で無関係: packages/ui/README.md
- 記録: docs/superpowers/plans/ の 40 件
```

「ずれた側」は次のどれかにする。どちらに合わせて直すかは、レビューを頼んだ側が決める。

- 文書が古い: 実装が変わり、文書が追いついていない（対象の変更や `git log` で、実装が後から変わったと分かる）
- 実装が外れた: 文書の規約・設計から、実装が外れている
- 判断が要る: 文書と実装のどちらに合わせるかを、repo の中から決められない

## 判断の目安

- ドリフトにするのは、その記述を信じた人・agent が実装と違う行動をとる食い違いだけ。言い換えや、正しいが粗い説明は指摘しない
- 記録（日付付きの plan・spec、ADR、CHANGELOG、議事録）は書いた時点の計画や決定なので、実装と違ってもドリフトにしない。現行の文書が記録を今の仕様として参照していれば、その記録も全文読んで突き合わせる。現行か記録か決められない文書は現行として扱い、指摘に「記録なら対象外」と添える
- これから作るものを書いた設計（実装中の設計書を含む）は、まだ無いことをドリフトにしない。既にあるものとして書かれた部分（既存の関数、変更するファイル、使う table）は、今の実装と突き合わせる
- signature と型は、呼ぶ側から見た形（引数の数と型、推論された戻り値の型）で比べる。型の別名や引数名の違いはドリフトにしない
- 記載漏れは、網羅を示す一覧から漏れているときだけ指摘する
- 文書同士が食い違うときは、どちらの記述も実装の事実と並べて示す
- 文言から白黒を付けられないものは「要確認」に理由付きで分ける。ドリフトに混ぜると、確実な指摘まで疑われる
- 対象が repo 全体でないとき、読む途中で気づいた対象と無関係なドリフトは「既存」にまとめる。今回の変更で直すものと、別途直すものを区別するため
