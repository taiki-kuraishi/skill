# PoC の結果

2026-11 に、このフローを 1 つの API で通したときの事実。PoC の repo は `/tmp` に置いただけで、恒久には残さない。

## 題材

project とコメントの API。Hono・drizzle-orm・bun:sqlite で、endpoint は 5 本（コメント作成、resolve、reopen、project 削除、コメント一覧）。定理は 3 つ。

- 対象の project があるとき、その member でない user の request は 403 になり、DB を変えない
- コメント ID が重複していなければ、未解決のコメントを resolve してから reopen すると、DB は元に戻る
- member が project を消すと、project とそのコメントが消え、他の project のコメントは残る

## 確かめたかったことと結果

| 確かめたかったこと              | 結果                                                                                                                                           |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| user が定理を読んで判断できるか | 3 つの定理を、指摘なしで承認した                                                                                                               |
| AI が証明を書き切れるか         | 書き切れた。証明役の subagent が主張やモデルを変えたくなった箇所は無かった                                                                     |
| 突き合わせがバグを拾えるか      | モデルが表せるバグは 5 回中 5 回、並行性は 0 回（下の表）                                                                                      |
| 実装のコードレビューを省けるか  | 実装を人が読まずに 2 回承認した。手順 5 の review は、突き合わせを通った実装に 15 件の問題を見つけ、どれも突き合わせでは見つからない種類だった |

## わざと入れたバグの検出（3000 run を 5 回ずつ）

| バグ                              | 種類       | 検出                       |
| --------------------------------- | ---------- | -------------------------- |
| 作成の member 判定を外す          | 認可       | 5/5                        |
| reopen で resolved が true のまま | 状態の遷移 | 5/5                        |
| 一覧を id の降順にする            | 並び順     | 5/5                        |
| 外部キーの cascade を外す         | 削除の連鎖 | 5/5（300 run では約 7 割） |
| 確認と insert の間に await を戻す | 並行性     | 0/5                        |

一覧を読む操作が無かったときは、他のコメントまで更新するバグを 300 run で見逃した。一覧の API を足し、各 run の最後に一覧を読むようにしてから、毎回見つかるようになった。

## Lean と Dafny の比較

同じモデルと定理を両方で書き、2 つのモデルを 300 run 突き合わせて一致を確かめた。user は、主張の読みやすさで Dafny を選んだ。

| 観点                   | Lean 4.35                                      | Dafny 4.11                           |
| ---------------------- | ---------------------------------------------- | ------------------------------------ |
| 主張の書き方           | `∀ … → … → …`                                  | `requires` / `ensures`               |
| 証明の手間（subagent） | コンパイル 6 回、約 15〜20 分、193 行          | verify 7 回、約 4 分、348 行         |
| 証明の飛ばしの検出     | `#print axioms` に `sorryAx` などが出る        | `dafny audit` に出る（exit は 0）    |
| 突き合わせへのつなぎ   | 実行ファイルを run ごとに起動（1 回 約 30 ms） | 生成した JS を直接呼ぶ（1 回 数 µs） |
| 信頼する部分           | Lean のカーネルとコンパイラ                    | Z3、Boogie、JS への変換器            |

## 実装役の subagent

最初の実装（156 行）で、突き合わせに食い違うことなく通った。所要は約 1 分。

## 検査 script をやめた経緯

証明役の subagent が主張を書き換えて検査を通すのを防ぐため、最初は検査 script（`check.sh`）を作った。手順 5 の review で 4 つ、攻撃役の subagent で 4 つの抜け道が見つかった（未追跡ファイルを見ない、base の既定値が HEAD、古いビルド成果物を読む、証明を `True` にすり替えられる、ビルド中の改ざん、git の index・`info/exclude`・`git replace` の細工など）。承認済み commit を書き出して検査する形まで作り込んだが、管理が重いので、主張の書き換えと証明の飛ばしだけを止める 2 コマンドに置き換えた。

## 確かめていないこと

- 既に E2E テストがある API に、後から入れたときの手間
- Cloudflare Workers・D1 で動かしたときの差
- 検出率の統計的な幅（各 5 回だけ）
- Dafny と Z3 を上げた後も証明が通るか
